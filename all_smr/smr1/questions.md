## Тема: Система володінь та запозичень у Rust. Особливості системи типів Rust.

---

## 1. Способи обійти систему володінь та запозичень

### Однопотоковий контекст

**`Cell<T>` та `RefCell<T>` — внутрішня мутабельність (interior mutability)**

Rust забороняє мати одночасно `&T` і `&mut T` на одне значення. `Cell` та `RefCell` дозволяють обійти це обмеження в однопотоковому контексті.

`Cell<T>` працює через копіювання: метод `get()` повертає копію значення, `set()` замінює його. Ніяких посилань на внутрішній вміст не видається — тому гарантії не порушуються. Підходить лише для типів що реалізують `Copy`.

`RefCell<T>` переносить перевірку правил запозичення з часу компіляції на час виконання. Метод `borrow()` повертає `Ref<T>`, `borrow_mut()` — `RefMut<T>`. Усередині зберігається лічильник: якщо є активний `RefMut`, будь-яке нове запозичення викличе паніку. Гарантії зберігаються завдяки runtime-перевірці — просто пізніше, ніж зазвичай.

```rust
use std::cell::RefCell;

let data = RefCell::new(vec![1, 2, 3]);
data.borrow_mut().push(4); // дозволено навіть через &RefCell
println!("{:?}", data.borrow()); // [1, 2, 3, 4]
```

**`Rc<T>` — спільне володіння в однопотоковому контексті**

`Rc<T>` дозволяє мати кілька власників одного значення через підрахунок посилань. Компілятор не дозволяє мутацію через `Rc` напряму, тому зазвичай використовується разом з `RefCell`: `Rc<RefCell<T>>`.

```rust
use std::rc::Rc;
use std::cell::RefCell;

let shared = Rc::new(RefCell::new(0));
let clone1 = Rc::clone(&shared);
*clone1.borrow_mut() += 1;
println!("{}", shared.borrow()); // 1
```

Гарантії зберігаються тому що `Rc` не є `Send` — передати його в інший потік неможливо на рівні типів.

**`unsafe` — явна відмова від перевірок**

`unsafe` блок дозволяє використовувати сирі вказівники (`*mut T`, `*const T`) без перевірок компілятора. Програміст бере на себе відповідальність за коректність. Це єдиний спосіб справжнього "обходу" системи — решта лише переносять перевірки.

### Багатопотоковий контекст

**`Arc<T>` — спільне володіння між потоками**

`Arc<T>` (Atomic Reference Counted) — потокобезпечна версія `Rc<T>`. Лічильник посилань оновлюється атомарно, тому `Arc` є `Send + Sync`. Для мутації використовується `Arc<Mutex<T>>` або `Arc<RwLock<T>>`.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0u64));
let handles: Vec<_> = (0..4).map(|_| {
    let c = Arc::clone(&counter);
    thread::spawn(move || { *c.lock().unwrap() += 1; })
}).collect();
handles.into_iter().for_each(|h| h.join().unwrap());
println!("{}", *counter.lock().unwrap()); // 4
```

Гарантії зберігаються завдяки `Mutex`: лише один потік може тримати блокування одночасно.

**`Mutex<T>` та `RwLock<T>`**

`Mutex<T>` надає взаємне виключення: `lock()` блокує поточний потік поки не отримає доступ. `RwLock<T>` дозволяє кільком читачам або одному писачу одночасно.

**Atomic типи — lock-free мутація**

`AtomicUsize`, `AtomicBool`, `AtomicPtr` тощо дозволяють змінювати прості значення без блокувань через процесорні атомарні інструкції. Не порушують гарантій бо операції є неподільними на апаратному рівні.

**`UnsafeCell<T>` — фундамент interior mutability**

Всі перераховані механізми базуються на `UnsafeCell<T>` — єдиному типі в Rust який дозволяє отримати `*mut T` з `&T`. Це законний спосіб: компілятор знає про `UnsafeCell` і не оптимізує такі доступи агресивно. Все що побудовано поверх нього (Cell, RefCell, Mutex) залишається безпечним через власну логіку синхронізації.

## 2. Методи конвертації між типами

### `From` / `Into`

`From<T>` визначає інфалібельне перетворення з типу `T`. `Into<T>` реалізується автоматично для будь-якого типу що реалізує `From`. Загальне правило: реалізовувати `From`, отримувати `Into` безкоштовно.

```rust
let s = String::from("hello");   // From<&str> для String
let n: i64 = i32::MAX.into();    // Into<i64> для i32
```

Використовується для перетворень що завжди успішні. Широко застосовується в обробці помилок: `impl From<IoError> for AppError` дозволяє використовувати `?` оператор.

### `TryFrom` / `TryInto`

Фалібельна версія `From`/`Into` — повертає `Result`. Використовується коли перетворення може не вдатися.

```rust
use std::convert::TryFrom;
let x = i8::try_from(200i32); // Err — 200 не вміщується в i8
let y = i8::try_from(42i32);  // Ok(42)
```

### `AsRef` / `AsMut`

Дозволяють отримати посилання на інший тип без передачі власності. Використовуються в параметрах функцій для гнучкості: `fn process(data: impl AsRef<[u8]>)` приймає і `Vec<u8>`, і `&[u8]`, і `String`.

```rust
fn print_len(s: impl AsRef<str>) {
    println!("{}", s.as_ref().len());
}
print_len("hello");           // &str
print_len(String::from("hi")); // String
```

### `Borrow`

Схожий на `AsRef`, але з додатковою семантичною вимогою: реалізація `Borrow<T>` означає що запозичений тип поводиться ідентично оригіналу стосовно `Hash`, `Eq`, `Ord`. Використовується в колекціях (`HashMap::get` приймає `K: Borrow<Q>`), що дозволяє шукати `String` ключ за `&str` без аллокації.

```rust
use std::collections::HashMap;
let mut map: HashMap<String, i32> = HashMap::new();
map.insert("key".to_string(), 42);
println!("{:?}", map.get("key")); // Some(42) — &str через Borrow
```

### `Deref` / `DerefMut`

Визначають поведінку оператора `*`. `String` реалізує `Deref<Target = str>`, `Vec<T>` — `Deref<Target = [T]>`. Це основа deref coercion: компілятор автоматично застосовує `Deref` коли потрібно перетворити тип. `Box<T>` → `T`, `Arc<T>` → `T`, `String` → `str`.

```rust
fn takes_str(s: &str) {}
let owned = String::from("hello");
takes_str(&owned); // автоматичний deref coercion &String → &str
```

**Відмінності між трейтами:**

| Трейт | Тип результату | Семантика |
|-------|----------------|-----------|
| `From`/`Into` | Власне значення | Перетворення з передачею власності |
| `TryFrom`/`TryInto` | `Result` | Фалібельне перетворення |
| `AsRef`/`AsMut` | Посилання | Дешеве запозичення як інший тип |
| `Borrow` | Посилання | Як `AsRef` але з гарантіями Hash/Eq/Ord |
| `Deref`/`DerefMut` | Посилання | Оператор `*` та автоматичне приведення |

### Крейти для зменшення бойлерплейту

**`derive_more`** — derive-макрос для автоматичної реалізації `From`, `Into`, `Display`, `Error` та інших. Замість ручного `impl From<X> for Y` достатньо `#[derive(From)]`.

**`strum`** — автоматична генерація конвертацій для enum: `FromStr`, `Display`, ітерація по варіантах.

**`from_str_derive`**, **`num_enum`** — конвертація між числами та enum.

## 3. Макроси в Rust

### Декларативні макроси (`macro_rules!`)

Визначаються через `macro_rules!` і працюють через зіставлення з образцем на рівні токенів. Це текстові шаблони що розгортаються компілятором.

```rust
macro_rules! say_hello {
    () => { println!("Привіт!"); };
    ($name:expr) => { println!("Привіт, {}!", $name); };
}
say_hello!();          // Привіт!
say_hello!("Оля");     // Привіт, Оля!
```

Приклад з `std`: `vec![]`, `println!`, `assert_eq!`, `matches!` — всі є декларативними макросами.

### Процедурні макроси

Це функції що отримують потік токенів (`TokenStream`) і повертають новий потік токенів. Виконуються під час компіляції як окремий крейт.

Три види:
- **derive-макроси** (`#[derive(Debug, Clone)]`) — генерують реалізації трейтів
- **атрибутні макроси** (`#[tokio::main]`, `#[route("/")]`) — трансформують елементи
- **функціональні макроси** (`sql!("SELECT * FROM users")`) — виглядають як виклики функцій

Приклади з відомих крейтів:
- `serde::Serialize/Deserialize` — автоматична серіалізація через derive
- `thiserror::Error` — derive для типів помилок
- `tokio::main` — атрибутний макрос що обгортає `main` в async runtime
- `sqlx::query!` — перевірка SQL запитів під час компіляції

### Відмінності

| Характеристика | Декларативні | Процедурні |
|----------------|-------------|------------|
| Синтаксис | `macro_rules!` | Окремий крейт з `proc-macro = true` |
| Потужність | Зіставлення з образцем | Повна маніпуляція AST |
| Складність | Простіші | Складніші у написанні |
| Hygiene | Гігієнічні | Залежить від реалізації |
| Приклади | `vec!`, `println!` | `#[derive(Debug)]`, `#[tokio::main]` |

### Обмеження макросів

- Макроси не можуть генерувати нові ідентифікатори у зовнішньому scope без явного передавання
- Не можна визначити макрос і одразу використати його в тому ж файлі до точки визначення (у декларативних)
- Процедурні макроси мають виконуватися в окремому крейті
- Макроси ускладнюють читання коду та налагодження — помилки компіляції вказують на розгорнутий код
- Не можна передавати макроси як аргументи функцій

### Коли макроси недоцільні

- Коли задачу можна вирішити звичайною функцією або trait — функції краще для тестування та документування
- Коли macro_rules! стає нечитабельним і складним — краще процедурний макрос або рефакторинг
- Для простих перетворень типів — `From`/`Into` достатньо
- Коли код виконується рідко і продуктивність не критична — зайва складність не виправдана
