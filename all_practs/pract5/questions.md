1. Які способи передачі даних між потоками ви знаєте? Які переваги та недоліки кожного із них?

Канали (mpsc, sync_channel) — потоки спілкуються через FIFO чергу, передаючи власність даних. Переваги: чітка модель власності, відсутність гонок, зручно для pipeline-архітектури. Недоліки: затримки на серіалізації передачі, складніше для малих обсягів даних. Мютекси з спільною памяттю (Arc<Mutex<T>>) — кілька потоків мають доступ до одних даних через блокування. Переваги: швидко для невеликих структур, природно для shared state. Недоліки: можливі deadlock, contention при високій конкуренції. Атомарні типи (AtomicUsize) — для простих скалярних значень. Переваги: lock-free, дуже швидко. Недоліки: тільки для простих типів.

2. Які способи спільного доступу до даних між потоками ви знаєте? Які переваги та недоліки кожного із них?

Arc<T> для read-only доступу — спільне володіння через підрахунок посилань. Переваги: безпечно і швидко для незмінних даних. Arc<Mutex<T>> — взаємне виключення. Переваги: універсально. Недоліки: блокування, можливість deadlock. Arc<RwLock<T>> — багато читачів або один писач. Переваги: масштабується для read-heavy навантажень. Атомарні типи — для одиночних значень без блокування. Channels — передача замість спільного доступу.

3. Що станеться з Mutex, якщо потік, який ним володіє, запанікує?

Mutex стає "отруєним" (poisoned). Наступний потік що спробує lock() отримає Err(PoisonError). Це механізм безпеки: панікуючий потік міг залишити дані у некоректному стані, тому Rust змушує інші потоки явно вирішити що з цим робити. При бажанні можна продовжити роботу з даними попри отруєння викликом into_inner().

4. Чи може тип бути Send, але не Sync? Наведіть приклад.

Так. Send означає що значення можна передати у інший потік. Sync означає що &T можна передавати між потоками. Класичний приклад — RefCell<T>: його можна перенести в інший потік (Send), але не можна дати два посилання на нього з різних потоків (не Sync), бо RefCell дозволяє внутрішню мутабельність без синхронізації.

5. Чому в Rust неможливі класичні "data races", але все ще можливі "race conditions"?

Data race — це коли два потоки одночасно звертаються до памяті без синхронізації. Rust забороняє це через правила запозичення: або багато &T, або одне &mut T. Race condition — це ширше поняття: коли результат залежить від порядку виконання потоків навіть якщо доступ синхронізовано. Наприклад, два потоки читають лічильник, потім обидва записують +1 — лічильник збільшиться лише на 1. Кожен окремий доступ коректний, але логіка послідовності неправильна. Rust не може це виявити бо це питання алгоритму.
